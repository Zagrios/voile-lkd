## M3 behaviors that depend on the 4 KiB page (READ unless stated)
Main finding (READ): this CrossOver Wine already contains all the "host page larger than the Windows page" code (113 uses of host_page_size/host_page_mask in virtual.c, written for arm64 at 16 KiB): protections computed as the union of the 4 KiB pages of a host page (get_host_page_vprot, mprotect_range), guard pages and stacks aligned on the host page, file views that fall back to read() when the host alignment is missing, release and decommit at host grain. On x86-64 it was fixed at 4 KiB. Fix: host_page_size becomes variable on x86-64 Linux, sysconf value (4 KiB, behavior unchanged) or WINE_HOST_PAGE_SIZE=16384 (same variable read by wineserver). Built, not measured because of wine-2. Decision per behavior:
1. KUSER_SHARED_DATA MAP_SHARED 4 KiB at 0x7ffe0000: fixed in Wine (64 KiB block reserved, dispatcher pointer at 0x7ffe4000). MEASURED: no more mm EINVAL.
2. PAGE_GUARD and PAGE_NOACCESS next to an accessible page in the same host page (thread stack guard, growing stack, VirtualProtect PAGE_GUARD from applications): do not fault in hardware. Wine: with WINE_HOST_PAGE_SIZE=16384 Wine's stack guards are placed on a whole host page (virtual_alloc_thread_stack, grow_thread_stack). A 4 KiB guard placed by an application in the middle of an accessible host page stays invisible: report to the lead (mm would have to signal the access another way, not doable with the hardware union; INFERRED: no effect for stacks managed by Wine).
3. Write watches (MEM_WRITE_WATCH, used by the .NET/Mono GCs and some engines): MEASURED userfaultfd ENOSYS, so Wine takes the mprotect + write fault path, at host_page_size grain. With 16 KiB, one write marks the four 4 KiB pages (conservative reporting, correct for a GC). Wine fix = WINE_HOST_PAGE_SIZE; nothing to ask of LKD.
4. Section views at 4 KiB offsets (NtMapViewOfSection, PE images whose RVA and file offset differ modulo 16 KiB): mm refuses (address and offset must have the same position within the 16 KiB page); READ map_file_into_view: EINVAL falls back to read() for a private or read-only view. Loss of semantics only for a misaligned writable MAP_SHARED view (memory shared between processes): to report to the lead if a real case shows up.
5. MAP_SHARED of small objects shared with wineserver (session __wine_session, shared queue/window objects, file mappings): Wine fix for the session (64 KiB); the other sections created by the server follow the 64 KiB granularity of Windows views (INFERRED); to measure.
6. Executable pages and data in the same host page (.text/.data sections of an image at 4 KiB): union = RWX in hardware, the engine's SMC detection handles the writes (MEASURED: "SMC write fault" messages at each startup, without error). Nothing to do in Wine.
7. Order of the top of the space: `preloader: failed to reserve range 7ffffe000000-7fffffff0000` (MEASURED): the guest is limited to 0x3fffffff0000; Wine adapts (host addr space limit). Nothing to do.

## Shaders "argument handle is unknown": cause found and fixed
- MEASURED (evidence/eac-runs/20261003T002813, diagnostic logs on both sides): 18,650 CreateVertex/PixelShader logged on the client side, all 18,650 decoded on the host side, none failed; the unknown ids (0x4434/0x4435, 0x61d1/0x61d2…) were NEVER created by CreateVertexShader/CreatePixelShader on the client side.
- Cause (READ, generated client code): for a Get with an object output (VSGetShader, PSGetShader, OMGetDepthStencilState, RSGetState…, and the slots of array Get*), the client places a new guest id in the output BEFORE sending, then wraps this id without knowing whether the host returned NULL (the reply does not say). When nothing is bound, the host returns NULL and registers nothing; the game (state save/restore around a render pass, typically an overlay) then calls VSSetShader/PSSetShader/OMSetDepthStencilState again with this wrapper: "argument handle is unknown", command dropped. Under Windows, VSGetShader returns NULL and the restore unbinds the shader.
- Fix (renderer, our G/virgl copy, npt_context.c/.h): a guest id whose host object is NULL is remembered (null_ids table); a lookup of this id returns NULL without failure, so Set* unbinds as under Windows; the COM release of the id removes it. The diagnostic logs of the creations were removed, the log of failed Creates and the one of late registrations stay. Patch: patches/virgl-null-guest-ids.patch.
- Addition: the generated host code of the 41 Get* dispatchers (npt_protocol_host_*.h) only registered the output if it was non-NULL (`if (args.X && *args.X)`); the null_ids table therefore saw nothing. Changed to `if (args.X)` in our copy (renderer rebuilt, logs/wine-linux-m6-virgl-build-006.log). To check at the next run (expected: no more "unregistered id … type 61/65").

## Input latency, Scaleform text, renderer copies (in progress, 2026-10-03 01:00 and after)
Tools added (tests only, disabled by default):
- wsd: WSD_LATENCY_PROBE=1. A WSD_DEBUG_INPUT injection arms a probe; each frame received afterwards is compared on a 48x27 luminance grid to the frame received just before the injection; the first frame whose difference exceeds 4 times the frame-to-frame noise (at least 1.5) is the game's reaction ("REACT"). Common clock: wsd's now_ns() = CLOCK_UPTIME_RAW = guest CLOCK_MONOTONIC under LKD (READ: src/lkd/src/task/time.c).
- driver: WINE_OBELISK_LATENCY=1 logs for each key the delay wsd event -> read and -> NtUserSendHardwareInput returned.
- eac-run.py: GUEST_EXTRA_ENV="A=1;B=2" adds guest variables, limited to the prefixes WINE_OBELISK_ and NPT_.
- renderer: NPT_TRACE_TEXUPD=<n> (texture update paths) and NPT_TRACE_UNMAP=1 (bytes copied by Unmap every 5 s).
- run/play-freeplay.sh: full route (title, probes at the menu, Free Play, pause probes, 60 s of driving with sample, exit through the menus), window captures only.

Latency (MEASURED):
- wsd -> driver -> Wine server: read of the event 0.04 to 0.05 ms after its creation, NtUserSendHardwareInput returned at 0.06 to 0.12 ms (first key 0.67 ms). Neither wsd, nor the driver's event thread (woken by event, blocking read), nor the Wine server, nor the LKD sockets add delay.
- Before the fix (run 20261003T011303): visible reaction at the menu (arrows) 77 to 130 ms, i.e. 7 to 9 frames at 60 fps; pause in Free Play 64 to 77 ms, leaving pause 120 to 134 ms; car start (W) 96 ms.
- Cause 1 (READ + MEASURED): DXGI allows 3 frames ahead; Neptune holds them in the WSI queue while nptunix waits for the display of the previous one: at the menu (limited by the display) each input waits 2 to 3 more frames. Neptune fix: NPT_PRESENT_QUEUE (default 1); Present waits until at most one previous frame is still on its way to the display. Run 20261003T012346: menu 67 to 111 ms (median about 80), same throughput while driving (21.9 ms versus 21.5).
- Cause 2 (MEASURED, run 20261003T013654): in nptunix, a ready frame waited up to 16 ms ("pacing wait" 14 to 16 ms) for the display of the previous one before being sent, then waited again for the next refresh. Fix: NPT_WSD_PACING=after (default): the frame leaves as soon as its fence is signaled, and the display wait happens after the send.

Renderer copies (MEASURED):

- Fix (Neptune client + renderer): DYNAMIC buffers whose only bind flags are VERTEX_BUFFER/INDEX_BUFFER are no longer sent at Unmap; each draw sends only the bytes it reads (vertex range of the bound buffers, index range, and vertex range of an indexed draw obtained by walking the indices, which are in guest memory).
